# 첫 Harness 프레임워크 릴리스 — OpenClaw의 "지속적 진화" 경험을 엔터프라이즈급 보안 경계 안으로

지난 글에 이어서, 이전 글에서 나는 OpenClaw와 그 배후에 있는 Harness Engineering 실천법을 깊이 파고들었고, 그 철학을 엔터프라이즈 에이전트 개발에 어떻게 적용할 수 있는지 설명하기 위해 "Harness Framework"의 밑그림을 그렸다.

좋은 소식은 AgentScope Java 1.1.0이 정식으로 출시되었다는 것이다. 이번 마일스톤 릴리스에서 우리는 "Harness Framework" 계획을 완전히 구현했다. 개발자는 1.1을 사용해 XxxClaw나 Coding Agent와 같은 로컬 생산성 앱뿐 아니라, DataAgent나 SRE Agent와 같은 분산 시나리오용 엔터프라이즈 앱까지 Harness를 빠르게 실천해볼 수 있다.

AgentScope Java 1.1.0은 이번 릴리스에서 네 가지 핵심 역량을 제공한다.

+ **워크스페이스 기반 에이전트 런타임**: 에이전트의 페르소나, 지식, 스킬, 메모리, 서브에이전트 스펙은 모두 구조화된 워크스페이스에 영속화된다. 매 실행마다 워크스페이스로부터 컨텍스트가 자동으로 로드되고, 실행 후에는 메모리가 자동으로 다시 기록되어, 시간이 지남에 따라 에이전트의 역량이 지속적으로 진화한다.
+ **플러그형 추상 파일 시스템**: 워크스페이스의 물리적 저장소는 로컬 디스크, 원격 공유 스토리지, 격리된 샌드박스 중 자유롭게 전환할 수 있으며, 모두 동일한 인터페이스를 통해 조작된다. 동일한 에이전트 로직을 수정 없이 개인 개발 환경과 엔터프라이즈 분산 배포 모두에 적용할 수 있다.
+ **즉시 사용 가능한 컨텍스트 관리**: 내장된 대화 압축(compaction), 계층화된 메모리 영속화, 전문 검색(full-text retrieval)이 장문 대화에서 컨텍스트가 부풀어 오르는 문제와 세션 간 메모리 유실이라는 고질적인 문제를 해결한다. 백그라운드 유지 관리 덕분에 메모리 저장소가 시간이 지나도 통제 불능으로 커지지 않는다.
+ **서브에이전트 오케스트레이션과 격리 실행**: 서브에이전트를 선언적으로 정의하고 서브태스크를 동기 또는 비동기로 위임하는 기능을 지원한다. 도구 실행은 격리된 샌드박스 안에서 동작하도록 구성할 수 있으며, 샌드박스 상태는 멀티턴 대화 간에도 복구 가능하고, 멀티테넌트 시나리오를 위한 세션 수준 및 사용자 수준 격리를 모두 지원한다.

## OpenClaw/Hermes는 훌륭한데, 왜 엔터프라이즈 에이전트 시나리오에서는 통하지 않는가?

지난 1년간 OpenClaw, Hermes, Claude Code와 같은 에이전트 제품들이 열풍을 일으켰고, 그 배후에 있는 Harness Engineering 철학 — 구조화된 워크스페이스, 컨텍스트 관리, 도구 컨벤션을 사용해 "매 대화가 처음부터 다시 시작되는" 원시적인 사용 패턴을 대체하는 것 — 도 함께 대중화되었다. 점점 더 많은 팀이 이 사고방식을 자신들의 에이전트 개발에 도입하고 있다.

그러나 실제로 이를 구현해보려는 이들은 흔히 "엔터프라이즈급"이라는 지점에서 길이 막힌다는 것을 발견한다. 우리는 현업 개발자들이 가장 자주 언급하는 다섯 가지 장애물을 정리했다.

1. **다중 사용자, 다중 레플리카 — 워크스페이스는 어떻게 할 것인가?** OpenClaw는 로컬 디렉터리를 워크스페이스로 사용하는데, 이는 단일 머신·단일 사용자에는 전혀 문제가 없다. 하지만 서비스가 외부로 노출되면 여러 사용자의 워크스페이스를 격리해야 하고, 에이전트가 여러 머신에 걸쳐 수평 확장되면 동일한 사용자의 워크스페이스가 레플리카 간에 공유되어야 한다 — 로컬 디렉터리라는 전제는 곧바로 깨진다.
2. **도구와 Skill 스크립트는 호스트에서 실행할 수 없는데, 어떻게 격리 실행할 것인가?** 에이전트가 Shell을 호출하거나 사용자 제공 코드를 실행하는 것은 신뢰할 수 있는 로컬 개발 머신에서는 문제가 없다. 하지만 일단 서비스화되면 사용자 입력을 그대로 호스트에서 실행하는 것은 보안 취약점이다. 샌드박스는 필수지만, "샌드박스가 있다"는 것은 첫걸음일 뿐이다. 샌드박스 안의 도구들도 전체 컨텍스트를 볼 수 있어야 하고, 동일한 샌드박스 인스턴스는 매번 처음부터 시작하는 것이 아니라 멀티턴 대화 간에 복구 가능해야 한다.
3. **"워크스페이스 + 파일 시스템" 조합을 어떻게 분산 환경으로 옮길 것인가?** 파일 시스템 기반 워크스페이스는 Harness Engineering에서 가장 직관적이고 효과적인 패턴이지만, 이는 "파일 시스템"에 의존한다. 분산 시나리오에는 통일된 로컬 디스크가 없으며, 원격 스토리지, KV 서비스, 오브젝트 스토리지는 저마다 다른 인터페이스를 갖는다. 하나하나 다시 작성하면 에이전트 로직이 인프라와 결합되어 버린다.
4. **Multi-Agent를 제대로 하려면 어떻게 해야 하는가?** 서브태스크 분배, 컨텍스트 격리, 비동기 실행, 결과 수집, 타임아웃 취소 — 개별적으로는 어렵지 않지만, 이를 관리 가능한 오케스트레이션 레이어로 조립하다 보면 코드 복잡도가 빠르게 치솟는다. 게다가 대부분의 프레임워크는 프리미티브만 제공할 뿐, "서브에이전트를 어떻게 선언하고, 언제 생성하며, 상태를 어떻게 관리할 것인가"라는 엔지니어링 문제는 각자의 몫으로 남겨둔다.
5. **컨텍스트 압축과 계층화된 메모리의 즉시 사용 가능한 구현이 존재하는가?** Harness Engineering은 이 두 가지를 매우 명확히 제시하지만, 실제로는 세부 사항이 무수히 많다: 압축 시점, 압축 전략, 압축 전 사실 추출, 이력 조회 가능성, 프로세스 재시작 후 복구... 대부분의 프레임워크는 단기/장기 메모리에 대한 추상 인터페이스만 제공할 뿐, 구체적인 구현은 여러분의 몫으로 남긴다.

이 다섯 가지 문제의 근본 원인은 하나다: **개인 비서형 에이전트와 엔터프라이즈 에이전트는 서로 다른 두 가지 엔지니어링 형태**이며, 동일한 전제를 두 시나리오 모두에 적용하면 반드시 벽에 부딪히게 된다.

**배포 형태** 관점에서 보면: 개인 비서는 단일 사용자·단일 프로세스이며, 모든 상태가 한 대의 머신에 존재해도 무방하다. 반면 엔터프라이즈 에이전트는 수평 확장하고, 다중 테넌트를 서비스하며, 서비스 중단이 없어야 하므로 상태는 분산 방식으로 저장·복구 가능해야 한다. **보안 경계** 관점에서 보면: 로컬 도구 실행에는 위험이 없지만, 프로덕션에서의 임의 Shell 실행은 심각한 공격 표면이다. 샌드박스와 권한 경계는 "선택적 최적화"가 아니라 "출시를 위한 전제 조건"이다. **운영 관측 가능성** 관점에서 보면: 개인 도구가 고장 나면 로그만 읽으면 되지만, 엔터프라이즈 서비스는 메모리 영속화, 세션 감사 가능성, 추적 가능한 상태 변화를 요구한다. **토큰 경제성** 관점에서 보면: 개인 사용자는 지연 시간과 비용에 민감하지 않지만, 엔터프라이즈 시나리오에서는 유효하지 않은 컨텍스트 재전송 하나하나가 실질적인 비용이다.

그렇다면 "한 벌의 로직을 작성하고 필요에 따라 형태를 전환"할 수 있게 해주는 프레임워크가 있을까? AgentScope Java 1.1.0의 Harness 모듈(진입 클래스 `HarnessAgent`)은 바로 이 목표를 겨냥해 설계되었다: `ReActAgent` 추론 루프를 대체하는 것이 아니라, 루프의 핵심 시점에 훅(hook)을 삽입하고, 한 벌의 도구·워크스페이스 컨벤션을 추가하며, 위의 다섯 가지 문제에 대한 엔지니어링적 해답을 패키징함으로써 여러분이 인프라가 아니라 에이전트의 비즈니스 로직에 집중할 수 있게 한다.

## AgentScope Harness 설계 철학: 왜 위 문제들을 풀 수 있는가?

AgentScope Harness의 설계 철학은 한 문장으로 요약할 수 있다: **"다음 턴은 어떻게 할 것인가, 다음 날은 어떻게 할 것인가, 컨텍스트가 폭발하면 어떻게 할 것인가, 상태가 유실되면 어떻게 할 것인가"에 대한 엔지니어링적 해답을 패키징하여, 모든 에이전트 프로젝트가 이를 매번 다시 발명하지 않도록 한다.**

구현 수준에서는 두 개의 핵심 기둥이 프레임워크 전체를 떠받친다.

### 핵심 기둥 1: source of truth로서의 워크스페이스

Harness는 모든 에이전트에 대해 **워크스페이스**라는 개념을 도입한다 — 에이전트 실행에 필요한 모든 영속 콘텐츠를 담는 구조화된 디렉터리로, 페르소나 정의(`AGENTS.md`), 장기 메모리(`MEMORY.md`), 도메인 지식(`knowledge/`), 재사용 가능한 스킬(`skills/`), 서브에이전트 스펙(`subagents/`), 세션 이력(`agents/<agentId>/`)을 포함한다.

이는 새로운 아이디어가 아니다 — OpenClaw와 Hermes 모두 실전에서, 에이전트에게 안정적인 "작업대"를 주는 것이 매번 다시 초기화하는 것보다 훨씬 효과적이라는 사실을 발견했다. Harness는 이 직관을 체계화한다: 워크스페이스는 에이전트의 단일 source of truth이며, 모든 상태 읽기/쓰기는 코드, 데이터베이스, 메모리에 흩어지는 대신 워크스페이스를 중심으로 이루어진다.

실제 동작에서는, 매 추론 턴이 시작되기 전에 `WorkspaceContextHook`이 `AGENTS.md`, `MEMORY.md`, `knowledge/` 등 핵심 파일을 자동으로 시스템 프롬프트에 주입하여, 에이전트의 페르소나와 지식이 매 턴마다 온전히 제시되도록 보장한다. 에이전트 실행이 끝난 후에는 `MemoryFlushHook`이 대화에서 새로운 사실을 추출해 메모리 파일에 기록하고, 이후 백그라운드의 `MemoryConsolidator`가 주기적으로 실행 로그를 정제된 장기 메모리로 병합한다. 워크스페이스는 대화를 거치며 지속적으로 진화하고, 매 실행마다 지난번보다 사용자와 태스크에 대해 "더 많이 아는" 상태가 된다.

### 핵심 기둥 2: 워크스페이스가 어떤 환경에서도 동작하게 하는 AbstractFilesystem

워크스페이스라는 아이디어는 매력적이지만, 실용적인 제약이 하나 있다: 로컬 디스크 디렉터리는 분산 시나리오에서 통하지 않는다. 여러 파드(pod)는 각자 자신만의 로컬 디스크를 갖는데, `MEMORY.md`는 어디에 기록되는가? 어느 레플리카의 버전이 "진짜" 버전인가?

AgentScope Harness는 **AbstractFilesystem**이라는 추상화 레이어로 이 문제를 해결한다. 상위 레이어에서 에이전트는 `read/write/ls/grep`과 같은 통일된 인터페이스만 호출하면 되며, "파일"이 실제로 어디에 저장되는지는 신경 쓰지 않는다. 하위 레이어에서는 로컬 디스크, 원격 오브젝트 스토리지(OSS), KV 데이터베이스(Redis), 샌드박스 파일 시스템, 그 밖의 어떤 매체로도 적응시킬 수 있으며, `CompositeFilesystem`을 통해 서로 다른 경로를 서로 다른 백엔드로 라우팅할 수도 있다.

이 파일 시스템 추상화를 기반으로, AgentScope 프레임워크는 에이전트 개발에 세 가지 주요 엔지니어링 역량을 직접 가져다준다.

**보안과 격리**

+ Shell/Code/Skill 실행은 샌드박스 백엔드를 통해 격리되며, 사용자 입력에 의해 구동되는 명령은 더 이상 호스트에서 직접 실행되지 않는다.
+ 워크스페이스 자체도 샌드박스 안에서 실행될 수 있어, 파일 읽기/쓰기 수준의 격리를 달성한다.
+ 도구 등록과 노출은 프레임워크가 일괄적으로 관리하며, 백엔드가 샌드박스 인터페이스를 구현한 경우에만 `execute` 도구가 나타난다.

**분산 배포**

+ 에이전트는 동등한 레플리카로 배포될 수 있으며, `MEMORY.md`와 세션 로그 같은 핵심 파일은 Remote 백엔드를 통해 공유 스토리지로 라우팅되어, 자연스럽게 노드 간 동기화를 달성한다.
+ `IsolationScope`(SESSION / USER / AGENT / GLOBAL)와 `RuntimeContext`의 조합을 통해, 코드 변경 없이도 세션 수준 격리와 사용자 수준 공유 등 여러 테넌트 전략을 구현할 수 있다.

**서브에이전트와 비동기 태스크**

+ 서브에이전트의 워크스페이스, 파일 시스템, 세션 상태는 부모 에이전트로부터 상속받거나 독립적으로 구성될 수 있으며, 오케스트레이션 전략은 스펙으로 선언되어 수동 조립이 필요 없다.
+ 비동기 태스크 상태 머신(PENDING/RUNNING/COMPLETED/FAILED/CANCELLED)과 결과 수집 메커니즘은 즉시 사용 가능하며, 프로세스 간(cross-process) 구현으로 교체하는 것도 지원한다.

## AgentScope Harness의 대표 사용 사례: 여러분의 시나리오에 빠르게 대응시키기

아래 세 가지 시나리오는 개인용부터 엔터프라이즈까지 대표적인 개발 형태를 아우른다. 이들은 상호 배타적인 선택지가 아니라, 서로 다른 세 가지 복잡도 경로를 나타낸다 — 가장 단순한 것부터 시작해 요구 사항이 진화함에 따라 점진적으로 옮겨갈 수 있다.

### 개인 에이전트 — 전형적인 OpenClaw 스타일 앱

**이 시나리오의 특징**: 단일 사용자, 로컬 머신 실행, 로컬 파일을 조작하거나 스크립트를 실행해야 함. 전형적인 제품은 개인 비서, 노트 봇, 로컬 Coding Agent다.

이 시나리오의 핵심 요구는 "에이전트가 진짜로 나를 알고 기억하게 만드는 것"이지, 상태를 갖지 않는 질의응답 기계가 되는 것이 아니다. 여기서 Harness의 가치는: 워크스페이스 안의 `AGENTS.md`가 에이전트의 페르소나와 행동 선호를 정의하고; 대화가 끝나면 새로운 사실이 자동으로 추출되어 메모리에 기록되며; 다음에 열었을 때도 에이전트는 여전히 당신을 알아보고 이전 진행 상황을 기억한다. 스킬과 도메인 지식 역시 워크스페이스에 존재하며, 코드를 건드리지 않고도 언제든 편집·조정할 수 있다.

로컬 배포에서는 Shell 실행도 활성화할 수 있어, 에이전트가 스크립트를 직접 실행하고 파일 시스템을 조작할 수 있다 — 이것이 OpenClaw 스타일 제품의 가장 매력적인 부분이다. Harness는 그 위에 "지속적 진화" 레이어를 더한다: 워크스페이스는 에이전트의 뇌와 같아서, 대화할 때마다 더 노련해진다.

**이 시나리오에서 AgentScope Harness가 제공하는 핵심 역량:**

+ **지속적인 메모리**: 대화가 끝나면 새로운 사실이 자동으로 추출되어 워크스페이스에 기록된다. 다음에 시작할 때 에이전트에게 배경을 다시 "알려줄" 필요가 없으며, 장기 메모리는 사용할수록 쌓인다.
+ **로컬 Shell 실행**: 신뢰할 수 있는 로컬 환경에서, 에이전트는 스크립트를 직접 실행하고 파일을 조작할 수 있어, OpenClaw 스타일 제품의 핵심 경험을 재현한다.
+ **설정으로서의 워크스페이스**: `AGENTS.md`를 수정해 페르소나를 조정하고, `skills/` 디렉터리에 스킬을 추가한다 — 파일 하나를 바꾸는 것이 에이전트를 한 번 업그레이드하는 것과 같으며, 재컴파일이나 재배포가 필요 없다.
+ **프로세스 간 세션 복구**: 닫았다가 다시 열어도, sessionId가 변하지 않는 한 이전 대화 상태가 완전히 복원되며, 처음부터 시작하지 않는다.

### 엔터프라이즈 데이터 서비스 — 전형적인 DataAgent

**이 시나리오의 특징**: 다수의 사용자를 서비스하고, SQL/Python/Shell을 실행해야 하며, 태스크가 오래 걸리고, 입력은 신뢰할 수 없는 외부 사용자로부터 오며, 멀티턴 대화 상태 복구와 레플리카 간 일관된 사용자 경험이 필요함.

이 시나리오의 가장 큰 리스크는 **실행 안전성**이다 — 사용자가 구동하는 코드가 서버에서 제한 없이 실행되어서는 안 된다. Harness의 샌드박스 메커니즘은 에이전트의 파일 조작과 명령 실행을 격리된 환경 안으로 가두며, 서버 프로세스 자체는 영향을 받지 않는다. 더 중요한 것은, 샌드박스가 "사용 후 파기"되지 않는다는 점이다: 매 턴이 끝날 때마다 샌드박스 상태가 영속화되어 다음 턴으로 이어지며, 서비스 재시작이나 노드 전환 때문에 사용자가 작업 진행 상황을 잃지 않는다.

멀티 레플리카 배포 시, 한 사용자의 장기 메모리(에이전트가 이 사용자에 대해 축적한 지식)는 공유 스토리지에 저장될 수 있어, 요청이 어느 노드에 도달하든 에이전트가 동일한 메모리를 보게 된다. 오래 걸리는 분석 태스크는 여러 개의 서브에이전트로 나뉘어 병렬 실행될 수 있으며, 메인 에이전트는 조정과 취합만 담당하므로 내내 블로킹되어 기다릴 필요가 없다.

**이 시나리오에서 AgentScope Harness가 제공하는 핵심 역량:**

+ **격리된 샌드박스 실행**: 모든 코드와 명령은 격리된 환경에서 실행되며, 호스트 서비스 프로세스는 사용자 입력의 영향을 받지 않고, 보안 경계가 명확하다.
+ **멀티턴 샌드박스 상태 복구**: 매 턴이 끝날 때마다 샌드박스 상태가 자동으로 저장되고 다음 턴 또는 서비스 재시작 시 그대로 복원되어, 사용자의 작업 현장이 사라지지 않는다.
+ **분산 메모리 공유**: 사용자 장기 메모리는 공유 스토리지에 저장되므로, 멀티 노드 배포에서 모든 레플리카가 "이 사용자에 대한 동일한 지식"을 읽어 일관된 경험을 제공한다.
+ **서브에이전트 병렬 오케스트레이션**: 긴 태스크를 여러 서브에이전트로 나누어 동시에 실행할 수 있으며, 메인 에이전트는 조정만 담당해 전체 효율을 높이고 타임아웃 및 실패 관리를 더 쉽게 만든다.
+ **멀티테넌트 격리**: 워크스페이스와 실행 환경은 세션 또는 사용자 차원으로 격리되어, 동시에 접속한 여러 사용자가 서로 간섭하지 않는다.

### 엔터프라이즈 온라인 서비스 — 전형적인 타오바오-티몰 거래 에이전트

**이 시나리오의 특징**: 태스크는 주로 비즈니스 API 호출(주문 생성, 조회, 승인 등)로 완료되며, 서버 측 Shell 실행은 필요 없지만, 다중 인스턴스 운영, 영속적인 세션 상태, 사용자 간 지식 공유가 필요함.

이 시나리오의 핵심 요구는 **안정성과 안전성**이다 — 온라인 서비스는 에이전트가 호출해서는 안 되는 Shell 명령을 호출했다는 이유로 장애가 나서는 안 된다. 여기서 Harness의 가치는: 샌드박스 실행 기능이 구성되지 않았을 때 프레임워크는 기본적으로 Shell 도구를 노출하지 않는다는 것이다. 에이전트는 오직 명확히 정의된 비즈니스 도구를 통해서만 외부와 상호작용할 수 있으며, 보안 경계는 개발자의 자율 규제가 아니라 설정에 의해 결정된다.

세션 상태와 메모리는 원격 스토리지에 영속화될 수 있으며, 여러 서비스 인스턴스가 동일한 사용자 메모리 세트를 공유한다. 사용자가 다른 진입점으로 전환해 새 대화를 시작하더라도, 에이전트는 여전히 이전 컨텍스트를 이어갈 수 있다. 여러 서브태스크(예: 재고 확인, 할인 계산, 요약 생성을 동시에 처리)를 병렬로 처리해야 할 때도 서브에이전트 메커니즘을 적용할 수 있으며, 외부 태스크 큐와 통합해 프로세스 간 태스크 관리도 가능하다.

**이 시나리오에서 AgentScope Harness가 제공하는 핵심 역량:**

+ **기본 보안 경계**: 샌드박스 실행이 활성화되지 않았을 때, 프레임워크는 Shell 도구를 노출하지 않는다. 에이전트는 여러분이 명시적으로 등록한 비즈니스 도구를 통해서만 외부와 상호작용할 수 있으며, 보안 정책은 설정에 의해 결정된다.
+ **다중 인스턴스 메모리 공유**: 세션 상태와 사용자 메모리는 원격 스토리지에 영속화되므로, 어떤 서비스 인스턴스든 동일한 컨텍스트를 읽을 수 있어 사용자가 인스턴스를 투명하게 전환할 수 있다.
+ **요청 간 세션 연속성**: 각 요청은 동일한 사용자 식별자를 담고 있으며, 에이전트는 이전 대화 상태를 자동으로 복원하여 진정한 멀티턴 연속 대화를 가능하게 한다.
+ **병렬 서브태스크 지원**: 여러 비즈니스 단계를 동시에 처리해야 할 때, 서브태스크를 서브에이전트에 위임해 병렬로 실행할 수 있으며, 결과는 취합된 후 통합된 응답으로 반환되어 메인 플로우의 응답 속도에 영향을 주지 않는다.

## AgentScope Harness 상세 — 잠시 시간을 내어 프레임워크에 대해 더 알아보기

이 섹션에서는 **사용자 관점**에서 AgentScope Harness의 핵심 역량을 설명한다: 무엇인지, 어떻게 동작하는지, 설정을 어떻게 생각해야 하는지.

### 빠른 시작

Harness를 시작하는 데는 세 단계면 충분하다: 의존성 추가, 워크스페이스 준비, `HarnessAgent` 빌드 및 호출.

**1. 의존성 추가**

```xml
<dependency>
    <groupId>io.agentscope</groupId>
    <artifactId>agentscope-harness</artifactId>
    <version>${agentscope.version}</version>
</dependency>

```

**2. 워크스페이스 준비**

디스크 위의 한 디렉터리를 `workspace`로 선택하고, 그 안에 `AGENTS.md`를 만든다. 이는 "선택적인 초기화 단계"가 아니라 Harness의 핵심 진입점이다 — 에이전트의 페르소나, 메모리, 스킬, 서브에이전트 스펙은 모두 이 디렉터리를 중심으로 이루어진다. 처음에는 `AGENTS.md` 안에 몇 줄의 컨벤션만 있어도 충분하며, 사용하면서 진화한다.

**3. `HarnessAgent` 빌드 및 호출**

```java
HarnessAgent agent = HarnessAgent.builder()
    .name("my-agent")
    .model(model)
    .workspace(Paths.get(".agentscope/workspace"))
    .compaction(CompactionConfig.builder()     // 프로덕션에서 컨텍스트 초과를 방지하려면 처음부터 설정하는 것을 권장
        .triggerMessages(50)
        .keepMessages(20)
        .build())
    .build();

RuntimeContext ctx = RuntimeContext.builder()
    .sessionId("user-session-001")   // 동일한 sessionId로 여러 번 호출하면 컨텍스트가 자동으로 이어짐
    .userId("alice")                 // 멀티유저 시나리오에서 네임스페이스 격리를 위해 필수
    .build();

Msg reply = agent.call(userMessage, ctx).block();
```

실행 후, 워크스페이스 디렉터리를 확인해보라: `AGENTS.md`, `memory/`, `agents/<agentId>/` 세 경로가 모두 존재해야 하며, 이는 에이전트가 이미 정상적으로 메모리를 기록하고 세션 상태를 영속화하고 있음을 나타낸다.

완전히 실행 가능한 예제는 `agentscope-examples/agents/harness-examples/harness-quickstart`의 `QuickstartExample`을 참고하라.

아래 여섯 가지 개념을 이해하면 사실상 Harness의 동작 논리를 파악한 것이다.

| 개념 | 정의 | 해결하는 문제 | 사용 제안 |
| --- | --- | --- | --- |
| `HarnessAgent` | `ReActAgent`를 기반으로 한 엔지니어링 래퍼 진입점. `build()` 시점에 훅, 내장 도구, 스킬, 세션 영속화를 조립한다. | "압축, 메모리, 세션, 서브태스크, 파일 시스템을 처음부터 조립하고 싶지 않다." | 비즈니스 코드는 `HarnessAgent.builder()`와 `agent.call(msg, ctx)`만 다루면 된다. |
| `workspace` | 에이전트의 작업 디렉터리로, `AGENTS.md`, `MEMORY.md`, `skills/`, `subagents/`, 세션 이력 등 모든 영속 콘텐츠를 담는다. | "페르소나, 지식, 메모리, 상태는 어디로 가며, 어떻게 지속적으로 진화하는가?" | 프롬프트를 작성하기 전에 워크스페이스 구조를 먼저 계획하라. 워크스페이스를 버전 관리 가능한 자산으로 취급하라. |
| `filesystem` | 파일 읽기/쓰기를 위한 통일된 인터페이스로, 에이전트 도구 레이어와 물리적 스토리지 사이의 추상화 레이어다. 로컬 디스크, 원격 스토리지, 샌드박스 등 다양한 백엔드를 지원한다. | "동일한 에이전트 로직이 로컬, 공유 스토리지, 샌드박스 사이를 어떻게 전환하는가?" | 세 가지 선언적 모드(Local / Remote / Sandbox) 중에서 우선 선택하라. |
| `RuntimeContext` | 한 번의 `call()`에 대한 신원 컨텍스트로, `sessionId`, `userId` 등을 포함한다. 매 호출마다 새로 전달되며 영속화되지 않는다. | "이번 턴은 누구이며, 상태는 어디에 읽고 쓰이며, 다중 테넌트는 어떻게 격리되는가?" | 항상 안정적인 `sessionId`를 전달하라. 멀티테넌트 시나리오에서는 `userId`가 필수다. |
| `sandbox` | 파일 조작과 명령이 샌드박스 측에서 실행되는 격리된 실행 환경. 매 턴이 끝나면 상태가 영속화되고 다음 턴에 복원된다. | "신뢰할 수 없는 입력 아래에서 어떻게 도구와 스크립트를 안전하게 실행하면서 멀티턴 상태 연속성을 유지하는가?" | 코드 실행 요구가 있을 때 먼저 활성화하라. 비즈니스에 따라 격리 단위를 선택하라. |
| `memory` | 2계층 메모리 시스템: 매 대화가 끝나면 새로운 사실이 자동으로 추출되어 실행 로그에 추가되고, 백그라운드 프로세스가 주기적으로 이를 주입 가능한 장기 메모리로 병합하며, 전문 검색을 지원한다. | "장문 대화에서 사실이 유실되지 않고, 컨텍스트가 폭발하지 않으며, 이력을 조회할 수 있다." | 대화 압축을 활성화하고 메모리 파일이 변하는 것을 지켜보라. 검색 도구를 사용해 오래된 사실을 복구하라. |


**요약**: `HarnessAgent`는 오케스트레이션을, `workspace`는 영속화를, `filesystem`은 저장 위치를, `RuntimeContext`는 신원을, `sandbox`는 경계를, `memory`는 장기 진화를 담당한다.

### 기능

#### 워크스페이스: 에이전트의 단일 source of truth

워크스페이스는 Harness를 일반적인 에이전트 프레임워크와 구별 짓는 가장 중요한 설계다. 이는 임시 저장 디렉터리가 아니라 에이전트의 "외부화된 뇌"다 — 세션을 넘나들며 유지되어야 하는 모든 것이 여기에 존재한다.

워크스페이스의 표준 디렉터리 구조는 다음과 같다.

```plain
workspace/
├── AGENTS.md              ← Agent persona and behavior conventions, automatically injected into system prompt before each reasoning turn
├── MEMORY.md              ← Refined long-term memory, maintained automatically by the background process and accumulated with use
├── knowledge/             ← Domain knowledge, injected together with AGENTS.md
├── skills/                ← Reusable skills, automatically assembled into the agent's tool set
├── subagents/              ← Subagent spec declarations, automatically discovered and loaded
└── agents/<agentId>/
    ├── context/           ← Session state snapshot (used for recovery after process restart)
    ├── sessions/          ← Dialogue JSONL and compacted context, for audit and retrieval
    └── memory/            ← Daily memory running log
```

**워크스페이스가 매 추론 턴에서 동작하는 방식**: 추론이 시작되기 전, Harness는 `AGENTS.md`, `MEMORY.md`, `knowledge/` 등 핵심 파일을 시스템 프롬프트에 조립한다. 추론이 끝나면, 대화에서 새로운 사실을 추출해 일일 메모리 실행 로그에 덧붙인다. 워크스페이스는 대화가 거듭될 때마다 지속적으로 진화하며, 에이전트는 시간이 지날수록 비즈니스와 사용자에 "더 익숙해"진다.

**워크스페이스가 코드에 프롬프트를 하드코딩하는 것보다 나은 이유**: 페르소나, 지식, 스킬, 서브에이전트 스펙은 모두 워크스페이스 파일 안에 있다. 동작을 조정하려면 파일만 바꾸면 되며, 재컴파일이나 재배포가 필요 없다. 복잡한 비즈니스 지식을 가진 에이전트에게 이는 특히 중요하다 — 비즈니스 규칙은 자주 바뀌며, 업데이트는 가벼워야 한다.

---

#### 세션 영속화: 요청과 프로세스를 넘나드는 지속적인 상태

Harness는 세션 상태 영속화를 **두 개의 병렬 경로**로 나누며, 각각 다른 문제를 해결한다.

+ **상태 스냅샷(`context/`)**: 매 `call()`이 끝난 후, 에이전트의 실행 상태(현재 대화 메모리, 도구 실행 컨텍스트 등)가 JSON 파일로 직렬화되어 워크스페이스의 `agents/<agentId>/context/<sessionId>/` 아래에 저장된다. 동일한 `sessionId`로 다음 호출이 이루어지면, 프레임워크는 추론 전에 이 스냅샷을 자동으로 로드해 지난번 끝난 지점으로 복원한다. 이것이 바로 "닫았다가 다시 열어도 지난번을 여전히 기억한다"는 것을 기술적으로 보장하는 요소다.
+ **대화 로그(`sessions/`)**: 전체 대화 이력이 JSONL 형식으로 `<sessionId>.log.jsonl`에 추가된다. 이 파일은 절대 압축되지 않으며 감사와 `session_search` 도구에 사용된다. 또 다른 파일인 `<sessionId>.jsonl`은 압축된 LLM 컨텍스트를 저장하며, 이는 모델이 실제로 "보는" 버전이다.

두 경로 모두 프레임워크가 자동으로 유지 관리한다. 개발자가 해야 할 유일한 일은 **매 호출마다 동일한 `sessionId`를 안정적으로 전달하는 것**뿐이다.

#### 메모리 관리: 대화에서 장기 지식으로의 자동 축적

이는 Harness의 가장 가치 있는 엔지니어링 역량 중 하나다. 많은 에이전트 프레임워크의 "메모리"는 사실상 이력 메시지를 컨텍스트에 쌓아 올리다가 결국 터져버리는 것이지만, AgentScope의 현재 접근 방식은 **2계층 분리**다.

**1계층 — 일일 실행 로그**: 매 대화가 끝나면, 프레임워크는 LLM을 사용해 대화에서 "새로운 사실"을 추출해 일일 메모리 파일(`memory/YYYY-MM-DD.md`)에 불릿 포인트 형태로 덧붙인다. 이 계층은 오직 추가만 하고 수정하지 않으며, 새로운 사실이 유실되지 않도록 보장한다.

**2계층 — 장기 메모리**: 백그라운드 스케줄러가 주기적으로 최근의 일일 실행 로그 파일을 읽고, LLM을 사용해 기존 `MEMORY.md`와 병합·중복 제거·정제한 뒤, 토큰 예산 안에서 "주입 가능한 버전"을 `MEMORY.md`에 다시 기록한다. 이 계층은 매 추론 턴에 주입되는 "사실 요약"이며, 품질이 높고 크기가 통제된다.

두 계층의 관계: 1계층은 **유실 없음**을 보장하고, 2계층은 **사용 가능성**을 보장한다. 새로운 사실은 먼저 실행 로그에 쌓이고, 충분히 축적되면 백그라운드 프로세스가 이를 장기 메모리로 옮긴다. 추론 중에 모델은 먼저 장기 메모리를 살펴보고, 찾지 못하면 `memory_search` 도구(SQLite FTS5 기반)를 사용해 전문 검색을 수행한다.

**컨텍스트 압축(Context compaction)**은 메모리 관리의 또 다른 측면이다: 메시지 수나 토큰 수가 임계값을 초과하면, Harness는 LLM을 사용해 이전 대화를 요약으로 압축하고, 가장 최근 메시지들을 유지하며, 나머지는 JSONL 파일로 내려보낸다. 압축은 장기 메모리 추출 이후에 이루어지며, 이는 가치 있는 정보가 압축되기 전에 먼저 침전되도록 보장한다. 모델이 컨텍스트 초과 오류를 반환하면, 프레임워크는 예외를 포착해 강제로 압축을 수행하고 자동으로 재시도한다. 이 전체 과정은 호출자에게 투명하다.

설정 제안:

```java
.compaction(CompactionConfig.builder()
    .triggerMessages(50)    // 메시지가 50개를 초과하면 압축을 트리거
    .keepMessages(20)       // 가장 최근 메시지 20개를 유지
    .flushBeforeCompact(true) // 압축 전에 메모리를 추출(기본적으로 활성화됨)
    .build())
```

#### 서브에이전트 오케스트레이션: 복잡한 태스크의 분해와 위임

메인 에이전트가 시간이 오래 걸리거나, 컨텍스트가 무겁거나, 병렬화 가능한 서브태스크를 만나면, 이를 서브에이전트에 위임해 실행할 수 있다. 서브에이전트는 독립적인 에이전트 인스턴스로서 자신만의 시스템 프롬프트와 메모리를 가지며, 메인 에이전트의 대화 이력을 공유하지 않고, 그 실행 결과는 도구 결과의 형태로 메인 에이전트에 반환된다.

**서브에이전트를 선언하는 방법은 네 가지**이며, 유연성이 낮은 것부터 높은 순서는 다음과 같다.

1. **내장 `general-purpose` 에이전트**: 메인 에이전트의 설정을 그대로 미러링하며, 임의의 서브태스크를 임시로 위임하기에 적합하다.
2. **워크스페이스 파일 기반**: `workspace/subagents/` 아래에 Markdown 파일을 배치하면(YAML front matter로 이름·설명·도구를 정의하고, 본문은 시스템 프롬프트), 프레임워크가 자동으로 발견하고 로드한다.
3. **코드 선언**: `builder.subagent(spec)`으로 프로그램적으로 지정한다.
4. **커스텀 팩토리**: 서브에이전트의 빌드 로직을 완전히 제어한다.

워크스페이스 기반 방식이 가장 권장된다 — 서브에이전트 정의가 워크스페이스와 함께 버전 관리되며, 코드를 건드리지 않고도 조정할 수 있다.

**호출 방식**은 동기와 비동기로 나뉜다.

+ **동기 호출**: 메인 에이전트는 서브에이전트가 완료될 때까지 블로킹 상태로 대기한 후 계속 진행한다. 결과 없이는 다음 단계로 넘어갈 수 없는 시나리오에 적합하다.
+ **비동기 호출**: 메인 에이전트는 태스크를 제출하고 즉시 태스크 ID를 받아, 다른 일을 계속할 수 있으며, 이후 `task_output` 도구로 결과를 폴링한다. 몇 초 이상 걸리는 태스크에는 비동기 방식이 강력히 권장되며, 이는 메인 에이전트가 블로킹되어 시간과 토큰을 낭비하는 것을 방지한다.

**무한 재귀 방지**: 서브에이전트는 기본적으로 "리프(leaf)" 형태이며 스스로 서브에이전트를 만들어낼 수 없다. 프레임워크는 또한 안전장치로 최대 깊이 제한을 두고 있다.

#### 내장 도구

`HarnessAgent`가 빌드될 때, 별도의 수동 설정 없이 "폐루프(closed-loop) 요구"를 아우르는 한 벌의 도구가 자동으로 등록된다.

| 도구 범주 | 도구 목록 | 설명 |
| --- | --- | --- |
| 파일 조작 | `read_file`, `write_file`, `edit_file`, `grep_files`, `glob_files`, `list_files` | 워크스페이스 파일을 조작하며, 경로는 파일 시스템 백엔드 범위 내로 제한된다 |
| 메모리 검색 | `memory_search`, `memory_get` | `memory_search`는 SQLite 전문 검색을 사용하고, `memory_get`은 줄 번호로 메모리 파일을 읽는다 |
| 세션 조회 | `session_search`, `session_list`, `session_history` | 에이전트가 능동적으로 검토할 수 있도록 과거 대화 내용을 조회한다 |
| 서브태스크 관리 | `agent_spawn`, `agent_send`, `agent_list`, `task_output`, `task_list`, `task_cancel` | 서브에이전트 태스크를 위임·조회·관리한다 |
| Shell 실행 | `execute` | **조건부 등록**: 파일 시스템 백엔드가 격리 실행을 지원할 때(로컬 Shell 모드 또는 샌드박스 모드)만 나타난다 |


주목할 점: "원격 공유 스토리지" 모드에서 프레임워크는 **기본적으로 Shell 도구를 등록하지 않는다** — 이는 의도적인 보안 설계이지 누락이 아니다. 여러분의 비즈니스 에이전트가 명령을 실행할 필요가 없다면, 이 모드는 실행 관련 보안 리스크 전체 범주를 제거해준다.

#### 파일 시스템: 세 가지 모드, 필요에 따라 선택

파일 시스템은 Harness에서 "에이전트 로직"과 "인프라"를 연결하는 핵심 레이어다. 프레임워크는 세 가지 선언적 모드를 제공하며, 비즈니스 제약에 따라 선택하면 된다.

**모드 1: Local + Shell(기본값)**

`filesystem`을 설정하지 않거나 명시적으로 `filesystem(new LocalFilesystemSpec())`을 작성하면, 워크스페이스는 로컬 머신 위의 디렉터리가 되며 Shell 명령을 실행할 수 있다. 개인용 로컬 앱과 개발/테스트 환경에 적합하며, 가장 단순하고 추가 의존성이 없다.

**모드 2: 원격 공유 스토리지**

`filesystem(new RemoteFilesystemSpec(store))`를 설정하면, 메모리와 세션 로그 같은 핵심 데이터는 원격 KV(예: Redis)로 라우팅되고, 로컬 파일 시스템은 공유할 필요가 없는 콘텐츠만 저장한다. **Shell 도구는 기본적으로 등록되지 않으며**, 멀티 레플리카 온라인 서비스와 사용자 메모리를 노드 간 공유해야 하지만 코드 실행은 필요 없는 시나리오에 적합하다.

**모드 3: 샌드박스 실행**

`filesystem(sandboxSpec)`을 설정하면, 파일 읽기/쓰기와 명령 실행이 모두 격리된 샌드박스 환경 안에서 완료되며, 호스트 프로세스는 영향을 받지 않는다. DataAgent나 Coding Agent처럼 신뢰할 수 없는 코드를 실행해야 하는 시나리오에 적합하다.

세 가지 모드의 핵심 차이는: **누가 명령을 실행하는지, 데이터가 어디에 저장되는지, 격리 단위가 무엇인지**다. 동일한 에이전트 코드 로직이 `filesystem` 설정 전환만으로 세 모드 사이를 이전할 수 있다.

---

#### 샌드박스: 격리된 실행 + 복구 가능한 상태

샌드박스 모드는 "격리된 실행"뿐 아니라 "멀티턴 대화 간 격리 환경의 연속성"까지 해결한다 — 이 둘을 합쳐야 진짜 중요한 것이 된다.

**실행 경계**: 샌드박스 모드에서는 에이전트가 호출하는 Shell 명령과 파일 읽기/쓰기가 샌드박스 측에서 일어나며, 호스트 프로세스는 조정만 담당한다. 사용자 입력으로부터 오는 임의의 명령이 서버에 직접적인 영향을 주지 않는다.

**상태 복구**: 매 `call()`이 끝나면, 샌드박스의 현재 파일 시스템 상태가 영속화된다(스냅샷 메커니즘). 다음 호출이 시작될 때, 프레임워크는 `sessionId` 또는 `userId`로 해당 스냅샷을 찾아 샌드박스를 지난번 끝난 지점으로 복원한다. 서비스 재시작이나 요청이 다른 노드로 흘러가더라도 사용자는 작업 진행 상황을 잃지 않는다.

**워크스페이스 투영(projection)**: `AGENTS.md`, `skills/`, `subagents/`, `knowledge/` 등 호스트 워크스페이스 콘텐츠는 매 `call()`이 시작될 때 샌드박스 안으로 동기화되며, 샌드박스 안의 에이전트가 완전한 설정과 스킬 정의를 보도록 보장한다.

**격리 단위**(필요에 따라 선택):

+ **세션 수준**: 세션마다 독립적인 샌드박스 상태를 가지며, 세션 간 간섭이 없다. 멀티유저 SaaS에 적합하다.
+ **사용자 수준**: 동일 사용자의 여러 세션이 동일한 샌드박스 상태를 공유한다. "사용자 장기 작업대" 시나리오에 적합하다.
+ **전역 공유**: 전체 에이전트가 하나의 샌드박스를 공유한다. 도구형이나 읽기 전용 에이전트에 적합하다.



실제 프로덕션 환경에서 샌드박스를 적용하는 것은 더 많은 고려 사항을 수반한다. 자세한 내용은 공식 문서를 참고하라.

+ 샌드박스 생명주기를 어떻게 관리할 것인가: 에이전트 내장 관리 또는 사용자 관리
+ 어떤 프로세스가 샌드박스 안에서 실행되어야 하는가: Tool In Sandbox, Subagent in Sandbox
+ 샌드박스 내부 상태를 어떻게 관리할 것인가: 상태, 스냅샷 복구

---

#### 스킬: 워크스페이스 기반 재사용 가능한 스킬

스킬은 "재사용 가능한 작업 워크플로우"를 구조화하는 방법이다. 워크스페이스의 `skills/<skill-name>/` 디렉터리 안에 `SKILL.md`를 배치하면, 프레임워크가 시작 시 이를 자동으로 발견하여 에이전트의 능력 라이브러리로 조립한다. 에이전트는 추론 중에 이러한 스킬들을 호출할 수 있으며, 스킬 자체는 "이 일을 어떻게 할지"에 대한 단계와 컨벤션을 기술한다.

이 설계의 엔지니어링적 가치는: 스킬은 파일이며, 코드와 함께 Git으로 버전 관리될 수 있고, 코드 리뷰가 가능하며, 재배포 없이 업데이트할 수 있다는 점이다. 팀이 에이전트에 주입해야 할 SOP와 운영 규범이 많을 때, 이는 모든 것을 시스템 프롬프트에 쌓아 넣는 것보다 훨씬 명확하다.

샌드박스 모드에서는 스킬 파일이 워크스페이스 투영과 함께 샌드박스로 동기화되며, 스킬에 관련된 명령은 격리된 환경에서 실행되어 호스트에 영향을 주지 않는다.

## 요약

AgentScope Java 1.1은 모두가 Harness Engineering으로부터 원하지만 스스로 조립하기는 가장 어려운 역량들을 **`HarnessAgent` + 워크스페이스 컨벤션 + 플러그형 파일 시스템 + 훅 파이프라인**으로 수렴시킨다: 개인용 시나리오에서는 메모리, 압축, 서브태스크가 가능한 강화된 ReAct Agent이며; 엔터프라이즈 시나리오에서는 **격리, 멀티테넌시, 분산 메모리, 서브에이전트 오케스트레이션**을 설정 항목으로 바꾸어주는 인프라다.

개인 비서 프로토타입에서 프로덕션 수준의 엔터프라이즈 에이전트로의 진화를 검토 중이라면, [Harness Overview](../overview.md)의 빠른 시작으로 시작한 뒤, [Filesystem](../filesystem.md)에서 선언적 모드를 하나 선택하고, 이후 필요에 따라 압축, 샌드박스, 서브에이전트를 활성화할 것을 권장한다 — 각 단계마다 대응하는 문서와 예제 모듈이 있어, "워크스페이스가 source of truth"라는 런타임을 처음부터 새로 발명할 필요가 없다.
