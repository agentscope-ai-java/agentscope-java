# Harness フレームワーク初リリース — OpenClaw の「継続的な進化」体験をエンタープライズグレードのセキュリティ境界の内側へ

前回の続きとして、以前の記事では OpenClaw とその背後にある Harness Engineering の実践を深く掘り下げ、その哲学をエンタープライズの agent 開発にどう適用できるかを説明するために「Harness Framework」を素描した。

良いニュースは、AgentScope Java 1.1.0 が正式にリリースされたことだ。このマイルストーンリリースにおいて、私たちは「Harness Framework」の計画を完全に実装した。開発者は 1.1 を使って Harness を素早く実践できる — XxxClaw や Coding Agent のようなローカルの生産性アプリケーションから、DataAgent や SRE Agent のような分散シナリオ向けのエンタープライズアプリケーションまで。

AgentScope Java 1.1.0 は今回のリリースで四つのコア機能を提供する:

+ **Workspace 駆動の agent ランタイム**: agent のペルソナ、知識、スキル、記憶、サブエージェント仕様はすべて構造化された Workspace に永続化される。実行のたびに、コンテキストは Workspace から自動的にロードされる。実行後、記憶は自動的に書き戻され、agent の能力は時間とともに継続的に進化する。
+ **プラガブルな抽象ファイルシステム**: Workspace の物理ストレージは自由に入れ替え可能である — ローカルディスク、リモート共有ストレージ、隔離されたサンドボックス — すべて同じインターフェースを通じて操作する。同じ agent のロジックを、コード変更なしに個人の開発環境からエンタープライズの分散デプロイまで適応させられる。
+ **すぐに使えるコンテキスト管理**: 組み込みの対話 compaction、階層化されたメモリの永続化、全文検索が、長い対話のコンテキスト肥大化とセッションをまたぐ記憶の喪失という厄介な問題を解決する。バックグラウンドのメンテナンスにより、メモリストアが時間とともに際限なく肥大化するのを防ぐ。
+ **サブエージェントのオーケストレーションと隔離実行**: サブエージェントの宣言的な定義と、サブタスクの同期または非同期の委譲をサポートする。ツール実行は隔離されたサンドボックス内で実行するよう設定でき、サンドボックスの状態は複数ターンの対話をまたいで復元可能であり、マルチテナントシナリオ向けに Session レベルとユーザーレベルの両方の分離をサポートする。

## OpenClaw/Hermes は素晴らしいが、なぜエンタープライズの agent シナリオでは機能しないのか?

この一年、OpenClaw、Hermes、Claude Code のような agent プロダクトが熱狂の波を巻き起こし、その背後にある Harness Engineering の哲学 — 構造化された Workspace、コンテキスト管理、ツールの規約を使って、「すべての会話がゼロから始まる」という原始的な利用パターンを置き換える — も広めた。ますます多くのチームが、この考え方を自分たちの agent 開発に取り入れている。

しかし、実際にそれを実現しようとした人々は、しばしば「エンタープライズグレード」のところで道が行き詰まることに気づく。私たちは、現場の開発者から最もよく挙げられる五つの障害を整理した:

1. **複数ユーザー、複数レプリカ — Workspace はどうするのか?** OpenClaw はローカルディレクトリを Workspace として使い、単一マシン・単一ユーザーには完全に問題ない。しかしサービスが外部に公開されると、複数ユーザーの Workspace は分離される必要があり、agent が複数マシンに水平スケールすると、同じユーザーの Workspace はレプリカ間で共有されなければならない — ローカルディレクトリの前提はすぐに破綻する。
2. **ツールと Skill スクリプトはホスト上で実行できない。どう隔離して実行するのか?** agent が Shell を呼び出したり、ユーザー提供のコードを実行したりすることは、信頼されたローカルの開発マシンでは問題ない。しかし一度サービスに入ると、任意のユーザー入力をホスト上で直接実行することはセキュリティ上の脆弱性になる。サンドボックスは必須だが、「サンドボックスがある」ことは第一歩にすぎない: サンドボックス内のツールも完全なコンテキストを見る必要があり、同じサンドボックスインスタンスは複数ターンの対話をまたいで復元可能でなければならず、毎回ゼロから始めるべきではない。
3. **「Workspace + ファイルシステム」の組み合わせをどう分散環境に移せるのか?** ファイルシステム駆動の Workspace は Harness Engineering において最も直感的で効果的なパターンだが、「ファイルシステム」に依存している。分散シナリオでは統一されたローカルディスクは存在せず、リモートストレージ、KV サービス、オブジェクトストレージはそれぞれ独自のインターフェースを持つ。それぞれについて書き直すことは、agent のロジックをインフラに結合させてしまう。
4. **Multi-Agent をどう正しく行うのか?** サブタスクの分配、コンテキストの分離、非同期実行、結果の収集、タイムアウトのキャンセル — それぞれの項目単体は難しくないが、それらを管理可能なオーケストレーション層に組み立てると、コードの複雑さが急速に増大する。さらに、ほとんどのフレームワークはプリミティブしか提供せず、「サブエージェントをどう宣言するか、いつ生成するか、状態をどう管理するか」というエンジニアリング上の問いは、自分で解決することが求められる。
5. **コンテキストの compaction と階層化されたメモリの、すぐに使える実装はあるのか?** Harness Engineering はこの二つのことを非常に明確にしているが、実際には詳細が多い: compaction のタイミング、compaction の戦略、compaction 前の事実抽出、履歴の検索可能性、プロセス再起動をまたいだ復元… ほとんどのフレームワークは短期/長期記憶の抽象インターフェースしか提供せず、具体的な実装は自分に任されている。

これら五つの問題の根本原因は同じことである: **個人アシスタント型の agent とエンタープライズ agent は、二つの異なるエンジニアリング上の形であり**、同じ前提を両方のシナリオに適用すれば、必ず壁にぶつかる。

**デプロイの形** という観点から見ると: 個人アシスタントは単一ユーザー・単一プロセスであり、すべての状態は一台のマシン上に存在しうる。エンタープライズ agent は水平にスケールし、複数のテナントにサービスを提供し、サービスを中断させないようにしなければならないため、状態は分散した形で保存・復元可能でなければならない。**セキュリティ境界** の観点から見ると: ローカルでのツール実行にはリスクはないが、本番環境での任意の Shell 実行は深刻な攻撃対象になる。サンドボックスと権限の境界は「あれば良いオプション」ではなく「本番投入の前提条件」である。**運用の可観測性** の観点から見ると: 個人向けツールが壊れたらログを読めばよいが、エンタープライズサービスにはメモリの永続化、Session の監査可能性、追跡可能な状態変化が必要である。**トークン経済** の観点から見ると: 個人ユーザーはレイテンシとコストに敏感ではないが、エンタープライズのシナリオでは、無効なコンテキストの再プッシュのすべてが実際のコストになる。

では、「一度ロジックを書き、必要に応じて形を切り替える」ことを可能にするフレームワークは存在するのだろうか? AgentScope Java 1.1.0 の Harness モジュール(エントリクラスは `HarnessAgent`)は、まさにこの目標に向けて設計されている: `ReActAgent` の推論ループを置き換えるのではなく、ループの重要な瞬間に hook を挿入し、ツールと Workspace の規約一式を追加し、上記五つの問題に対するエンジニアリング上の答えをパッケージ化することで、開発者がインフラではなく agent のビジネスロジックに集中できるようにする。

## AgentScope Harness の設計哲学: なぜこれらの問題を解決できるのか

AgentScope Harness の設計哲学は一文でまとめられる: **「次のターンはどうするか、次の日はどうするか、コンテキストが爆発したらどうするか、状態が失われたらどうするか」というエンジニアリング上の答えをパッケージ化する。すべての agent プロジェクトにそれを再発明させるのではなく。**

実装レベルでは、二つのコアの柱がフレームワーク全体を支えている。

### コアの柱 1: 唯一の正としての Workspace

Harness はすべての agent に対して **Workspace** という概念を導入する — agent が実行するために必要なすべての永続的な内容を運ぶ構造化されたディレクトリである: ペルソナの定義(`AGENTS.md`)、長期記憶(`MEMORY.md`)、ドメイン知識(`knowledge/`)、再利用可能なスキル(`skills/`)、サブエージェント仕様(`subagents/`)、Session の履歴(`agents/<agentId>/`)。

これは新しいアイデアではない — OpenClaw と Hermes はどちらも、agent に安定した「作業台」を与えることが、毎回それを再初期化するよりもはるかに効果的であることを実践の中で発見していた。Harness はこの直感を体系化する: Workspace は agent の唯一の正であり、すべての状態の読み書きはコード、データベース、メモリに散らばるのではなく、Workspace を中心に回る。

実際の動作では、各推論ターンの前に、`WorkspaceContextHook` が `AGENTS.md`、`MEMORY.md`、`knowledge/` などの重要なファイルを system prompt に自動的に注入し、agent のペルソナと知識が毎ターン完全に提示されることを保証する。agent の実行が終わった後、`MemoryFlushHook` は会話から新しい事実を抽出し、メモリファイルに書き込む。その後、バックグラウンドの `MemoryConsolidator` が定期的に実行ログを洗練された長期記憶にマージする。Workspace は会話を通じて継続的に進化し、実行のたびに前回よりもユーザーとタスクについて「より多くを知っている」。

### コアの柱 2: Workspace をあらゆる環境で動かす AbstractFilesystem

Workspace というアイデアは魅力的だが、実用上の制約がある: ローカルディスクのディレクトリは分散シナリオでは機能しない。複数の pod はそれぞれ自分のローカルディスクを持っている — `MEMORY.md` はどこに書かれるのか? どのレプリカのバージョンが「真実」なのか?

AgentScope Harness はこの問題を **AbstractFilesystem** 抽象レイヤーで解決する。上位レイヤーにとって、agent は `read/write/ls/grep` のような統一されたインターフェースを呼ぶだけでよく、「ファイル」が実際にどこに着地するかを気にする必要はない。下位レイヤーでは、ローカルディスク、リモートオブジェクトストレージ(OSS)、KV データベース(Redis)、サンドボックスのファイルシステム、その他任意のメディアに適応でき、さらに `CompositeFilesystem` を通じて異なるパスを異なるバックエンドにルーティングすることもできる。

このファイルシステム抽象の上に、AgentScope フレームワークは agent 開発に三つの大きなエンジニアリング上の能力を直接もたらす:

**セキュリティと隔離**

+ Shell/Code/Skill の実行はサンドボックスバックエンドを通じて隔離され、ユーザー入力によって駆動されるコマンドはもはやホスト上で直接実行されない。
+ Workspace 自体もサンドボックス内で実行できるため、ファイルの読み書きレベルでの隔離を実現する。
+ ツールの登録と公開はフレームワークによって統一的に管理される。`execute` ツールは、バックエンドがサンドボックスインターフェースを実装している場合にのみ現れる。

**分散デプロイ**

+ agent は対等なレプリカとしてデプロイでき、`MEMORY.md` や Session ログのような重要なファイルは Remote バックエンドを通じて共有ストレージにルーティングされ、ノードをまたいだ同期を自然に実現する。
+ `IsolationScope`(SESSION / USER / AGENT / GLOBAL)と `RuntimeContext` の組み合わせにより、Session レベルの分離やユーザーレベルの共有といった複数のテナント戦略を、コード変更なしに実現できる。

**サブエージェントと非同期タスク**

+ サブエージェントの Workspace、ファイルシステム、Session 状態は、親 agent から継承されるか、独立して設定される。オーケストレーション戦略は仕様によって宣言され、手動での組み立ては不要である。
+ 非同期タスクのステートマシン(PENDING/RUNNING/COMPLETED/FAILED/CANCELLED)と結果収集の仕組みはすぐに使える状態にあり、プロセスをまたぐ実装への置き換えをサポートする。

## AgentScope Harness の典型的なユースケース: あなたのシナリオに素早くマッピングする

以下の三つのシナリオは、個人からエンタープライズまでの典型的な開発の形をカバーしている。これらは互いに排他的な選択肢ではなく、三つの異なる複雑さのパスを表している — 最もシンプルなものから始め、要件の進化に応じて段階的に移行できる。

### 個人向け Agent — 典型的な OpenClaw スタイルのアプリ

**このシナリオの特徴**: 単一ユーザー、ローカルマシンでの実行、ローカルファイルの操作やスクリプトの実行が必要。典型的なプロダクトは、個人アシスタント、ノート取りボット、ローカルの Coding Agent である。

このシナリオでのコアのニーズは、「agent に本当に自分のことを知って覚えていてもらう」ことであり、ステートレスな Q&A マシンであることではない。ここでの Harness の価値は次の通りである: Workspace 内の `AGENTS.md` が agent のペルソナと行動の好みを定義し、会話の後に新しい事実が自動的に抽出されて記憶に書き込まれ、次に開いたときも agent はあなたを認識し、以前の進捗を覚えている。スキルとドメイン知識も Workspace に存在し、コードに触れることなくいつでも編集・調整できる。

ローカルデプロイでは、Shell 実行も有効にでき、agent がスクリプトを実行し、ファイルシステムを直接操作できるようになる — これが OpenClaw スタイルのプロダクトの最も魅力的な部分である。Harness はその上に「継続的な進化」というレイヤーを追加する: Workspace は agent の脳のようなものであり、会話のたびに経験を積んでいく。

**このシナリオで AgentScope Harness が提供するコア機能:**

+ **継続的な記憶**: 会話の後、新しい事実が自動的に抽出されて Workspace に書き込まれる。次回起動時に agent に背景を再度「伝える」必要はなく、長期記憶は使うほどに蓄積される。
+ **ローカルの Shell 実行**: 信頼されたローカル環境では、agent はスクリプトを直接実行し、ファイルを操作できる。OpenClaw スタイルのプロダクトのコア体験を再現する。
+ **設定としての Workspace**: `AGENTS.md` を変更してペルソナを調整し、`skills/` ディレクトリにスキルを追加する — 一つのファイルを変更することは、再コンパイルや再デプロイなしに agent を一度アップグレードすることに等しい。
+ **プロセスをまたぐ Session の復元**: 閉じて再度開く。sessionId が変わらない限り、以前の会話状態は完全に復元され、ゼロから始まることはない。

### エンタープライズのデータサービス — 典型的な DataAgent

**このシナリオの特徴**: 複数ユーザーへのサービス提供、SQL / Python / Shell の実行が必要、タスクに時間がかかる、入力は信頼できない外部ユーザーから来る、複数ターンの対話状態の復元とレプリカをまたいだ一貫したユーザー体験が必要。

このシナリオで最大のリスクは **実行の安全性** である — ユーザー主導のコードをサーバー上で無制限に実行させることはできない。Harness のサンドボックスメカニズムは、agent のファイル操作とコマンド実行を隔離された環境に閉じ込める。サーバープロセス自体は影響を受けない。さらに重要なのは、サンドボックスが「使い捨て」ではないことだ: 各ターンの後、サンドボックスの状態は永続化され、次のターンに持ち越される。そのため、ユーザーはサービスの再起動やノードの切り替えによって作業の進捗を失うことがない。

マルチレプリカのデプロイでは、ユーザーの長期記憶(agent がこのユーザーについて蓄積した知識)を共有ストレージに保存できるため、リクエストがどのノードに着地しても、agent は同じ記憶を見る。長い分析タスクは複数のサブエージェントに分割して並列実行でき、メインの agent は調整と集約のみを担当し、常に待機してブロックすることはない。

**このシナリオで AgentScope Harness が提供するコア機能:**

+ **隔離されたサンドボックスでの実行**: すべてのコードとコマンドは隔離された環境で実行され、ホストのサービスプロセスはユーザー入力の影響を受けず、セキュリティ境界が明確である。
+ **複数ターンにまたがるサンドボックス状態の復元**: 各ターンの後、サンドボックスの状態は自動的に保存され、次のターンやサービス再起動時にその場で復元されるため、ユーザーの作業現場は失われない。
+ **分散されたメモリ共有**: ユーザーの長期記憶は共有ストレージに保存されるため、マルチノードのデプロイでは、すべてのレプリカが「このユーザーについての知識」を同じように読み取り、一貫した体験を提供する。
+ **サブエージェントの並列オーケストレーション**: 長いタスクは並行して実行される複数のサブエージェントに分解でき、メインの agent は調整のみを行うため、全体の効率が上がり、タイムアウトと失敗の管理が容易になる。
+ **マルチテナント分離**: Workspace と実行環境は Session またはユーザーの次元で分離されるため、同時にオンラインの複数ユーザーが互いに干渉しない。

### エンタープライズのオンラインサービス — 典型的な Taobao-Tmall 取引 Agent

**このシナリオの特徴**: タスクは主にビジネス API の呼び出し(注文、照会、承認など)によって完了し、サーバー上での Shell 実行は不要だが、マルチインスタンスでの動作、永続的な Session 状態、ユーザーをまたぐ知識共有が必要。

このシナリオでのコアのニーズは **安定性と安全性** である — オンラインサービスは、agent が実行すべきでない Shell コマンドを呼び出したために失敗することがあってはならない。ここでの Harness の価値は次の通りである: サンドボックス実行機能が設定されていない場合、フレームワークはデフォルトで Shell ツールを公開しない。agent は明確に定義されたビジネスツールを通じてのみ外部とやり取りでき、セキュリティ境界は開発者の自己規律ではなく設定によって決まる。

Session の状態と記憶はリモートストレージに永続化でき、複数のサービスインスタンスが同じユーザーの記憶セットを共有する。ユーザーが別の入口に切り替えて新しい会話を始めても、agent は以前のコンテキストを引き続き使える。複数のサブタスクの並列処理が必要な場合(在庫の確認、割引の計算、サマリーの生成を同時に行うなど)、サブエージェントの仕組みも適用でき、外部のタスクキューと統合してプロセスをまたぐタスク管理も可能である。

**このシナリオで AgentScope Harness が提供するコア機能:**

+ **デフォルトのセキュリティ境界**: サンドボックス実行が有効化されていない場合、フレームワークは Shell ツールを公開しない。agent は明示的に登録されたビジネスツールを通じてのみ外部とやり取りでき、セキュリティポリシーは設定によって決まる。
+ **マルチインスタンス共有メモリ**: Session の状態とユーザーの記憶はリモートストレージに永続化されるため、どのサービスインスタンスも同じコンテキストを読み取ることができ、ユーザーはインスタンス間を透過的に切り替えられる。
+ **リクエストをまたぐ Session の継続性**: 各リクエストは同じユーザー識別子を運び、agent は自動的に以前の会話状態を復元するため、真の複数ターンの継続的な対話が可能になる。
+ **並列サブタスクのサポート**: 複数のビジネスステップを同時に処理する必要がある場合、サブタスクはサブエージェントに委譲されて並列実行され、結果は集約された後に統一的な返信として返され、メインフローの応答速度に影響を与えない。

## AgentScope Harness を詳しく見る — フレームワークについてもう少し学ぶ時間を

このセクションでは、AgentScope Harness のコア機能を **ユーザー視点** から説明する: それが何であるか、どう動くか、設定についてどう考えるか。

### クイックスタート

Harness を始めるにはたった三つのステップで済む: 依存関係を追加し、Workspace を準備し、agent を構築して呼び出す。

**1. 依存関係を追加する**

```xml
<dependency>
    <groupId>io.agentscope</groupId>
    <artifactId>agentscope-harness</artifactId>
    <version>${agentscope.version}</version>
</dependency>

```

**2. Workspace を準備する**

ディスク上のディレクトリを `workspace` として選び、その中に `AGENTS.md` を作成する。これは「任意の初期化ステップ」ではなく、Harness のコアとなるエントリポイントである — agent のペルソナ、記憶、スキル、サブエージェント仕様はすべてこのディレクトリを中心に回る。`AGENTS.md` の数行の規約だけで最初は十分であり、使ううちに進化していく。

**3. `HarnessAgent` を構築して呼び出す**

```java
HarnessAgent agent = HarnessAgent.builder()
    .name("my-agent")
    .model(model)
    .workspace(Paths.get(".agentscope/workspace"))
    .compaction(CompactionConfig.builder()     // 本番でのコンテキストオーバーフローを避けるため、最初から設定することを推奨
        .triggerMessages(50)
        .keepMessages(20)
        .build())
    .build();

RuntimeContext ctx = RuntimeContext.builder()
    .sessionId("user-session-001")   // 同じ sessionId での複数回の呼び出しはコンテキストを自動的に継続する
    .userId("alice")                 // マルチユーザーシナリオでの名前空間分離に必須
    .build();

Msg reply = agent.call(userMessage, ctx).block();
```

実行後、Workspace ディレクトリを確認する: `AGENTS.md`、`memory/`、`agents/<agentId>/` の三つのパスがすべて存在するはずであり、これは agent がすでに正常に記憶を書き込み、Session 状態を永続化していることを示している。

完全に実行可能な例については、`agentscope-examples/agents/harness-examples/harness-quickstart` の `QuickstartExample` を参照してほしい。

### コアコンセプト

以下の六つの概念を理解すれば、基本的に Harness の動作ロジックを把握したことになる。

| 概念 | 定義 | 解決する問題 | 使用上の提案 |
| --- | --- | --- | --- |
| `HarnessAgent` | `ReActAgent` を基盤とするエンジニアリング上のラッパーエントリポイント。`build()` 時に hook、組み込みツール、スキル、Session の永続化を組み立てる。 | 「compaction、記憶、Session、サブタスク、ファイルシステムをゼロから組み立てたくない。」 | ビジネスコードは `HarnessAgent.builder()` と `agent.call(msg, ctx)` だけを扱う。 |
| `workspace` | agent の作業ディレクトリ。`AGENTS.md`、`MEMORY.md`、`skills/`、`subagents/`、Session の履歴といったすべての永続的な内容を運ぶ。 | 「ペルソナ、知識、記憶、状態はどこに行き、どう継続的に進化するのか?」 | プロンプトを書く前に Workspace の構造を計画する。Workspace をバージョン管理可能な資産として扱う。 |
| `filesystem` | ファイルの読み書きのための統一インターフェース。agent のツール層と物理ストレージの間の抽象レイヤー。ローカルディスク、リモートストレージ、サンドボックスなどのバックエンドをサポート。 | 「同じ agent のロジックが、ローカル、共有ストレージ、サンドボックスをどう切り替えられるか?」 | 三つの宣言的モード(Local / Remote / Sandbox)から選ぶことを優先する。 |
| `RuntimeContext` | 単一の `call()` のアイデンティティコンテキスト。`sessionId`、`userId` などを含む。呼び出しごとに新しく渡され、永続化はされない。 | 「今回は誰のターンで、状態はどこに読み書きされ、複数のテナントはどう分離されるのか?」 | 常に安定した `sessionId` を渡すこと。マルチテナントのシナリオでは `userId` が必須。 |
| `sandbox` | 隔離された実行環境で、ファイル操作とコマンドはサンドボックス側で実行される。各ターンの後、状態は永続化され次のターンで復元される。 | 「信頼できない入力のもとでツールとスクリプトを安全に実行しつつ、複数ターンにわたる状態の継続性をどう維持するのか?」 | コード実行の需要があるときはまず有効にする。ビジネスに応じて分離粒度を選ぶ。 |
| `memory` | 二層構造の記憶システム: 各会話の後、新しい事実が自動的に抽出されて実行ログに追記される。バックグラウンドプロセスが定期的にそれらを注入可能な長期記憶へとマージし、全文検索を提供する。 | 「長い会話でも事実を失わず、コンテキストが爆発せず、履歴が検索可能であること。」 | 対話の compaction を有効にし、記憶ファイルの変化を観察する。検索ツールを使って古い事実を復元する。 |


**まとめ**: `HarnessAgent` はオーケストレーションを担当し、`workspace` は永続化を担当し、`filesystem` は着地点を担当し、`RuntimeContext` はアイデンティティを担当し、`sandbox` は境界を担当し、`memory` は長期的な進化を担当する。

### 機能

#### Workspace: Agent の唯一の正

Workspace は、Harness を一般的な agent フレームワークと区別する最も重要な設計である。それは一時的なストレージディレクトリではなく、agent の「外部化された脳」である — Session をまたいで保持する必要のあるすべてのものがここに存在する。

Workspace の標準的なディレクトリ構造は以下の通りである:

```plain
workspace/
├── AGENTS.md              ← Agent のペルソナと行動規約。各推論ターンの前に system prompt へ自動的に注入される
├── MEMORY.md              ← 洗練された長期記憶。バックグラウンドプロセスにより自動的にメンテナンスされ、使うほどに蓄積される
├── knowledge/             ← ドメイン知識。AGENTS.md と共に注入される
├── skills/                ← 再利用可能なスキル。agent のツールセットに自動的に組み込まれる
├── subagents/              ← サブエージェント仕様の宣言。自動的に発見・ロードされる
└── agents/<agentId>/
    ├── context/           ← Session 状態スナップショット(プロセス再起動後の復元に使用)
    ├── sessions/          ← 対話 JSONL と圧縮されたコンテキスト。監査と検索のため
    └── memory/            ← 日次のメモリ実行ログ
```

**各推論ターンにおける Workspace の動作**: 推論が始まる前に、Harness は `AGENTS.md`、`MEMORY.md`、`knowledge/` などの重要なファイルを system prompt に組み立てる。推論が終わった後、会話から新しい事実を抽出し、日次のメモリ実行ログに追記する。Workspace は会話のたびに継続的に進化し、agent は時間とともにビジネスとユーザーに「より精通」していく。

**なぜ Workspace はコード内にプロンプトをハードコードするより優れているのか**: ペルソナ、知識、スキル、サブエージェント仕様はすべて Workspace のファイルにある。振る舞いを調整するには、再コンパイルと再デプロイではなく、ファイルを変更するだけでよい。複雑なビジネス知識を持つ agent にとって、これは特に重要である — ビジネスルールは頻繁に変わり、更新は軽量であるべきだからだ。

---

#### Session の永続化: リクエストとプロセスをまたぐ継続的な状態

Harness は Session の状態の永続化を **二つの並行したパス** に分割し、それぞれが異なる問題を解決する:

+ **状態スナップショット(`context/`)**: 各 `call()` が終わるたびに、agent の実行状態(現在の対話メモリ、ツール実行のコンテキストなど)は JSON ファイルにシリアライズされ、Workspace 内の `agents/<agentId>/context/<sessionId>/` の下に保存される。次に同じ `sessionId` で呼び出しが行われると、フレームワークは推論の前にこのスナップショットを自動的にロードし、前回終了した状態に復元する。これが「閉じて再度開いても、前回のことをまだ覚えている」ことの技術的な保証である。
+ **対話ログ(`sessions/`)**: 完全な対話履歴は JSONL 形式で `<sessionId>.log.jsonl` に追記される。このファイルは決して compaction されず、監査と `session_search` ツールのために使われる。もう一つのファイル `<sessionId>.jsonl` は、圧縮された LLM コンテキストを保存する。これはモデルが実際に「見る」バージョンである。

両方のパスはフレームワークによって自動的にメンテナンスされる。開発者がすべきことは、**すべての呼び出しで同じ `sessionId` を安定して渡す**ことだけである。

---

#### メモリ管理: 対話から長期的な知識への自動的な沈殿

これは Harness の最も価値あるエンジニアリング上の機能の一つである。多くの agent フレームワークの「メモリ」は、本質的には、最終的に破裂するまで履歴メッセージをコンテキストに積み上げ続けるものである。AgentScope の現在のアプローチは **二層分離** である:

**レイヤー1 — 日次の実行ログ**: 各会話の後、フレームワークは LLM を使って会話から「新しい事実」を抽出し、それを箇条書きの形で日次のメモリファイル(`memory/YYYY-MM-DD.md`)に追記する。このレイヤーは追記のみで変更はせず、新しい事実が失われないことを保証する。

**レイヤー2 — 長期記憶**: バックグラウンドのスケジューラが定期的に最近の日次実行ログファイルを読み込み、LLM を使ってそれらを既存の `MEMORY.md` とマージ・重複排除・洗練し、トークン予算内で「注入可能なバージョン」を `MEMORY.md` に書き戻す。このレイヤーは、各推論ターンに注入される「事実のサマリー」であり、品質が高くサイズが制御されている。

二つのレイヤーの関係: レイヤー1 は **喪失しないこと** を保証し、レイヤー2 は **使いやすさ** を保証する。新しい事実はまず実行ログに着地し、十分に蓄積されると、バックグラウンドプロセスがそれらを長期記憶に移す。推論の間、モデルはまず長期記憶を見て、何かを見つけられなければ `memory_search` ツール(SQLite FTS5 に基づく)を使って全文検索を行う。

**コンテキストの compaction** はメモリ管理のもう一つの側面である: メッセージ数またはトークン数が閾値を超えると、Harness は LLM を使って以前の対話を要約に圧縮し、最新のメッセージを保持し、残りを JSONL ファイルにオフロードする。compaction は長期記憶の抽出の後に発生し、価値ある情報が圧縮される前に沈殿することを保証する。モデルがコンテキストオーバーフローのエラーを返した場合、フレームワークはその例外を捕捉し、強制的に compaction を行い、自動的にリトライする。このプロセス全体は呼び出し側にとって透過的である。

設定の提案:

```java
.compaction(CompactionConfig.builder()
    .triggerMessages(50)    // メッセージ数が 50 を超えたら compaction をトリガー
    .keepMessages(20)       // 直近 20 件のメッセージを保持
    .flushBeforeCompact(true) // compaction の前にメモリを抽出する(デフォルトで有効)
    .build())
```

#### サブエージェントのオーケストレーション: 複雑なタスクの分解と委譲

メインの agent が時間のかかる、コンテキストの重い、あるいは並列化可能なサブタスクに遭遇した場合、それをサブエージェントに委譲して実行させることができる。サブエージェントは独立した agent インスタンスであり、独自の system prompt と記憶を持つ。メインの agent の対話履歴を共有せず、その実行結果はツールの結果としてメインの agent に返される。

**サブエージェントを宣言する方法は四つある**。柔軟性の低いものから高いものへ:

1. **組み込みの `general-purpose` agent**: メインの agent の設定をそのまま反映する。任意のサブタスクを一時的に委譲するのに適している。
2. **Workspace ファイル駆動**: `workspace/subagents/` の下に Markdown ファイルを配置する(YAML front matter が名前、説明、ツールを定義し、本文が system prompt)。フレームワークが自動的に発見してロードする。
3. **コードによる宣言**: `builder.subagent(spec)` でプログラム的に指定する。
4. **カスタムファクトリ**: サブエージェントの構築ロジックを完全に制御する。

Workspace 駆動のアプローチが最も推奨される — サブエージェントの定義は Workspace と共にバージョン管理され、コードに触れることなく調整できる。

**呼び出し方法**は同期と非同期に分かれる:

+ **同期呼び出し**: メインの agent はブロックしてサブエージェントの完了を待ってから続行する。結果なしでは次のステップに進めないシナリオに適している。
+ **非同期呼び出し**: メインの agent はタスクを提出して即座にタスク ID を取得し、他のことを続けられ、後で `task_output` ツールで結果をポーリングできる。数秒以上かかるタスクには、非同期を強く推奨する。メインの agent がブロックして時間とトークンを無駄にすることを避けるためである。

**無限再帰の防止**: サブエージェントはデフォルトで「葉」の形であり、自分自身がさらにサブエージェントを生成することはできない。フレームワークには安全策として最大深度の制限もある。

---

#### 組み込みツール

`HarnessAgent` が構築されると、「クローズドループのニーズ」をカバーするツール一式を、手動の設定なしに自動的に登録する:

| ツールカテゴリ | ツール一覧 | 説明 |
| --- | --- | --- |
| ファイル操作 | `read_file`, `write_file`, `edit_file`, `grep_files`, `glob_files`, `list_files` | Workspace ファイルを操作する。パスはファイルシステムバックエンドの範囲内 |
| メモリ検索 | `memory_search`, `memory_get` | `memory_search` は SQLite の全文検索を使う。`memory_get` は行番号でメモリファイルを読む |
| Session の照会 | `session_search`, `session_list`, `session_history` | agent が能動的にレビューするための過去の対話内容を取得する |
| サブタスク管理 | `agent_spawn`, `agent_send`, `agent_list`, `task_output`, `task_list`, `task_cancel` | サブエージェントのタスクを委譲、照会、管理する |
| Shell 実行 | `execute` | **条件付きで登録される**: ファイルシステムバックエンドが隔離された実行をサポートする場合(ローカル Shell モードまたはサンドボックスモード)にのみ現れる |


注目すべき点: 「リモート共有ストレージ」モードでは、フレームワークは **デフォルトで Shell ツールを登録しない** — これは意図的なセキュリティ設計であり、見落としではない。ビジネスの agent がコマンドを実行する必要がない場合、このモードは実行のセキュリティリスクの一カテゴリ全体を排除する。

---

#### ファイルシステム: 三つのモード、必要に応じて選ぶ

ファイルシステムは、Harness において「agent のロジック」と「インフラ」を接続する重要なレイヤーである。フレームワークは三つの宣言的モードを提供する。ビジネスの制約に基づいて選ぶ:

**モード1: Local + Shell(デフォルト)**

`filesystem` を設定しない、あるいは明示的に `filesystem(new LocalFilesystemSpec())` と書くと、Workspace はローカルマシン上のディレクトリになり、Shell コマンドを実行できる。個人のローカルアプリや開発/テスト環境に適しており、最もシンプルで追加の依存関係がない。

**モード2: リモート共有ストレージ**

`filesystem(new RemoteFilesystemSpec(store))` を設定すると、メモリや Session ログのような重要なデータはリモート KV(例: Redis)にルーティングされ、ローカルファイルシステムは共有する必要のないコンテンツのみを保存する。**Shell ツールはデフォルトでは登録されない**。マルチレプリカのオンラインサービスや、コード実行は不要だがユーザーの記憶をノードをまたいで共有する必要があるシナリオに適している。

**モード3: サンドボックス実行**

`filesystem(sandboxSpec)` を設定すると、ファイルの読み書きとコマンドの実行はすべて隔離されたサンドボックス環境内で完結し、ホストプロセスは影響を受けない。DataAgent や Coding Agent のような、信頼できないコードを実行する必要があるシナリオに適している。

三つのモードの間のコアの違いは: **誰がコマンドを実行するか、データがどこに着地するか、分離の粒度はどうか** である。同じ agent のコードロジックは、`filesystem` の設定を切り替えるだけで三つのモード間を移行できる。

---

#### サンドボックス: 隔離された実行 + 復元可能な状態

サンドボックスモードは「隔離された実行」だけでなく、「複数ターンの対話をまたいだ隔離環境の連続性」も解決する — 両方合わせて初めて本当に重要になる。

**実行境界**: サンドボックスモードでは、agent が呼び出す Shell コマンドとファイルの読み書きはサンドボックス側で行われ、ホストプロセスは調整のみを行う。ユーザー入力からの任意のコマンドがサーバーに直接影響を与えることはない。

**状態の復元**: 各 `call()` が終わるたびに、サンドボックスの現在のファイルシステム状態が永続化される(スナップショットの仕組み)。次の呼び出しの開始時に、フレームワークは `sessionId` または `userId` で対応するスナップショットを見つけ、サンドボックスを前回終了した状態に復元する。サービスの再起動や別のノードへのリクエストの移動によって、ユーザーが作業の進捗を失うことはない。

**Workspace の射影**: `AGENTS.md`、`skills/`、`subagents/`、`knowledge/` のようなホストの Workspace の内容は、各 `call()` の開始時にサンドボックスに同期され、サンドボックス内の agent が完全な設定とスキル定義を見ることを保証する。

**分離の粒度**(必要に応じて選択):

+ **Session レベル**: 各 Session が独立したサンドボックス状態を持ち、Session 間の干渉がない。マルチユーザー SaaS に適している。
+ **ユーザーレベル**: 同じユーザーの複数の Session が同じサンドボックス状態を共有する。「ユーザーの長期作業台」シナリオに適している。
+ **グローバル共有**: agent 全体が一つのサンドボックスを共有する。ツール型または読み取り専用の agent に適している。



実際の本番環境でサンドボックスを適用するには、さらに多くの考慮事項がある。詳細は公式ドキュメントを参照:

+ サンドボックスのライフサイクルをどう管理するか: agent 組み込みの管理か、ユーザー管理か
+ どのプロセスをサンドボックス内で実行する必要があるか: Tool In Sandbox、Subagent in Sandbox
+ サンドボックス内部の状態をどう管理するか: state、スナップショットの復元

---

#### スキル: Workspace 駆動の再利用可能なスキル

スキルは「再利用可能な操作ワークフロー」を構造化する方法である。Workspace の `skills/<skill-name>/` ディレクトリに `SKILL.md` を配置すると、フレームワークは起動時にそれを自動的に発見し、agent の能力ライブラリに組み込む。agent は推論中にこれらのスキルを呼び出すことができる。スキル自体は「これをどうやるか」の手順と規約を記述する。

この設計のエンジニアリング上の価値は: スキルはファイルであり、コードと一緒に Git でバージョン管理でき、コードレビューでき、再デプロイなしに更新できる。チームに agent へ注入すべき大量の SOP と運用規範がある場合、これはすべてをシステムプロンプトに詰め込むよりもはるかに明確である。

サンドボックスモードでは、スキルファイルは Workspace の射影と共にサンドボックスに同期され、スキルに関わるコマンドはホストに影響を与えることなく隔離環境内で実行される。

## まとめ

AgentScope Java 1.1 は、誰もが Harness Engineering から求めているが自分で組み立てるのが最も難しい機能セットを、**`HarnessAgent` + Workspace の規約 + プラガブルなファイルシステム + hook パイプライン** へと収束させた: 個人向けシナリオでは、記憶を持ち、compaction を持ち、サブタスクを持つ強化された ReAct Agent であり、エンタープライズシナリオでは、**隔離、マルチテナンシー、分散メモリ、サブエージェントのオーケストレーション** を設定項目に変えるインフラである。

個人アシスタントのプロトタイプから本番対応のエンタープライズ agent への進化を評価しているなら、[Harness 概要](../overview.md) のクイックスタートから始め、[Filesystem](../filesystem.md) から宣言的なモードを選び、それから必要に応じて compaction、サンドボックス、サブエージェントを有効化していくことをお勧めする — それぞれのステップには対応するドキュメントとサンプルモジュールがあり、「Workspace こそが真実」というランタイムをゼロから発明する必要はない。
