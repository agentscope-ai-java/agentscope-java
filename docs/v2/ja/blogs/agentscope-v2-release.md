# AgentScope 2.0: 透明な開発からシステムエンジニアリングへ

AgentScope は agent アプリケーションを構築するためのオープンソースフレームワークであり、開発者が大規模言語モデルからデプロイ可能な agent へと進むのを助ける。今日の課題は、もはや agent に単一のリクエストへ答えさせることだけではない — それは agent に **タスクを確実にやり遂げさせる** ことである: 長く複数ステップにわたるワークフローを扱い、ツールを安全に呼び出し、外部システムときれいに統合することだ。

このニーズに応えるため、AgentScope 1.0 は *透明な開発* というアイデアを導入した: agent がメッセージを受け取り、ツールを呼び出し、協力者と調整する各ステップは、開発者にとって可視であるべきであり、理解、デバッグ、拡張のコストを下げる。AgentScope 2.0 はこの原則を引き継ぎ、本番運用の現実 — 安定した実行、制御された自律性、きれいな統合 — により真剣に焦点を当てる。その結果は、より完全で、より一貫性のあるシステムレベルのアップグレードである。

![AgentScope 2.0 runtime core modules at a glance](/imgs/v2/as2-release-01.png)

## 1. モデル統合: 開かれたエコシステムの上にフォールトトレランスを

![Model integration: open ecosystem + retry & fallback model](/imgs/v2/as2-release-02.png)

AgentScope 2.0 は 1.0 のオープンなモデル層 — Qwen、Anthropic、DeepSeek、Gemini、OpenAI — を維持しつつ、Grok や Moonshot のようなプロバイダーで拡張する。しかし 2.0 の本当の焦点は「より多くのモデル」ではない。それは、モデル呼び出しを **複雑なワークロードの下でも安定させる** ことである。

実際のタスクでは、agent は通常多くのラウンドの推論を実行し、多くのツール呼び出しをトリガーする。単一の失敗した、タイムアウトした、あるいは利用不能になったモデルの応答が、残りの実行を壊してしまうことがある。そのため AgentScope 2.0 は、モデル層に統一されたリトライとフォールバックモデルの仕組みを導入する。開発者は最大リトライ回数とフォールバックモデルを設定でき、プライマリモデルが失敗したとき、フレームワークは自動的にフォールバックを試み、タスクを前に進め続けられる。

このアップグレードは、agent がもはや「モデルを呼び出せる」というだけでなく、モデルと対話するためのより堅牢なランタイム戦略を持つことを意味する。継続的な推論と複数ステップの実行に依存するタスクにとって、モデル層での安定性は、agent がそもそもジョブをやり遂げられるかどうかの基盤となる。

## 2. メッセージとイベント: チャット文字列からインタラクティブな実行ストリームへ

![Unified message structure → event stream → UI follows in real time](/imgs/v2/as2-release-03.jpg)

agent アプリケーションの複雑さはメッセージにも現れる。チャットアプリでは、メッセージは単純な文字列でありうる。agent の実行の内部では、単一のメッセージがテキスト、画像、ファイル、ツール呼び出し、ツール結果、モデルの思考、ユーザー確認の状態、あるいは外部実行の結果を運ぶことがある。AgentScope 2.0 はメッセージモジュールを再構築し、これらすべてが統一された `Content Block` を通じて流れるようにする。その中で、`DataBlock` は base64 と URL の両方のデータソースをサポートし、異なるモデル API のマルチモーダルおよびファイル機能との整合を容易にする。

その基盤の上に、AgentScope 2.0 はイベントシステムを導入する。単一の agent の応答は、もはや最終的な文字列だけではなく — モデル呼び出しの開始、テキストの差分、ツール呼び出し、ツール結果、ユーザー確認、外部実行の更新といったイベントをストリームできる。これにより、フロントエンドの UI は agent の作業をリアルタイムでレンダリングでき、人間による確認、人間の介入、外部ツールの実行を、フレームワークのファーストクラスの機能に変える。例えば、agent が機密なツールを呼び出そうとしているとき、ユーザー確認を発火できる。ツールが外部環境で実行されるとき、agent は外部の結果を待ってからタスクを続行できる。

したがって、メッセージモジュールとイベントシステムへのアップグレードは、AgentScope の「透明」の原則を強化するだけにとどまらない。それらは agent の実行を **観測可能、インタラクティブ、そして中断可能** にする。開発者が目にするのは、もはや最終的な回答だけではなく — 展開されていく様子を見て、操縦できる実行ストリームである。

## 3. 権限システム: 境界づけられた自律性

![Permission system: static rules + tool type + input analysis → allow / ask / deny](/imgs/v2/as2-release-04.png)

大規模モデルを最大限に活用するには、agent には本当の自律性が必要である: 単に応答を生成するだけでなく、タスクの進行状況に基づいてツールを能動的に選び、情報を読み、行動を取ることだ。agent がより自律的になるほど、それが許される範囲の境界を明確に引くことがより重要になる。

AgentScope 2.0 は、agent がツールを呼び出し、ファイルを読み書きし、コマンドを実行する方法を統治する、より体系的な権限システムを導入する。ツール呼び出しはもはや二値の許可/拒否の決定ではない。静的なルール、ツールの種類、実際の入力に基づいて、AgentScope はある操作を許可すべきか、拒否すべきか、あるいはユーザー確認にエスカレートすべきかを判断できる。ファイルシステムツールは危険なディレクトリと機密ファイルをチェックする。コマンドツールは高リスクなコマンド、動的なシェル構文、破壊的な削除を分析する。未知の、あるいは高リスクな挙動については、AgentScope はその呼び出しを自動的にユーザー承認フローにルーティングできる。

この仕組みにより、agent はもはや単に「ツールを呼び出せる」だけでなく、**明示的で制御可能な境界の内側で** 自律的に行動できる。継続的なツール利用、ファイルアクセス、コマンド実行に依存する複雑なタスクにとって、この安全境界は、agent が安定してジョブを完了できるかどうかのもう一つの基盤となる。

## 4. 再構築されたコンテキスト管理: 長時間タスクとパフォーマンスをサポート

![Context management: structured compaction + tool-result offloading + file-IO cache](/imgs/v2/as2-release-05.png)

長時間のタスクを扱うことは、agent アプリケーションを現実世界にもたらす上で最も重要なステップの一つである。長時間のタスクは、多くのラウンドのモデル呼び出し、多くのツール結果、大きなファイルの内容、そして継続的なユーザーフィードバックを伴いうる。コンテキスト管理が「履歴をウィンドウに圧縮する」ところで止まってしまうと、新しい問題がすぐに現れる: どの情報を保持すべきか、どのツール結果を切り詰めるべきか、同じファイルの再読み込みをどう避けるか、長い実行チェーンにわたってタスクの状態の一貫性をどう保つか、といったことだ。

AgentScope 1.0 はすでにコンテキスト管理の機能を提供していた。2.0 では、それらの機能がより体系的になった。AgentScope 2.0 は、タスクの状態、ツール結果、ファイル I/O と一緒にコンテキストを管理する: compaction はもはや単なるフラットな要約ではなく — タスクの目標、現在の状態、主要な発見、次のプラン、長期的に保持しなければならない情報を構造化された形で保存する。ツール結果は切り詰められ、大きすぎるログ、検索結果、ファイルの内容がコンテキストウィンドウを爆発させないようにする。組み込みのファイルツールには読み取りキャッシュが追加され、繰り返しの I/O を削減し、既存ファイルを編集する操作にはまずファイルを読み込むことを要求することで、パフォーマンスと運用の信頼性の両方を改善する。

AgentScope 2.0 において、コンテキスト管理はもはや単なる「履歴の圧縮」ではない。それは **長時間タスクの実行を持続させるためのシステムレベルの戦略** へとアップグレードされた。これにより、agent はタスクの状態をより整理された形で維持し、コンテキストがどれだけ大きくなるかを制御し、継続的な推論と繰り返しのツール呼び出しの中でも安定を保てる。

## 5. ミドルウェア: より柔軟な拡張サーフェス

![Middleware: hook into key execution stages of the agent](/imgs/v2/as2-release-06.png)

実際の agent は、しばしば独自のロギング、権限ポリシー、ビジネスコンテキスト、モデル呼び出し戦略を必要とする。これらの機能のすべてをフレームワークの内部を変更することで追加しなければならないとしたら、拡張のコストは上がり — フレームワークの安定性へのリスクも上がる。

AgentScope 2.0 は **ミドルウェア** の仕組みを導入し、開発者が agent の重要な実行段階にカスタムロジックを注入できるようにする: モデル呼び出しの前後でのログトレース、ツール実行前のセキュリティチェック、reasoning-and-acting ループの内側でのビジネスポリシー、そして system prompt 構築段階での動的なコンテキスト注入だ。ミドルウェアにより、AgentScope 2.0 はコアフレームワークを安定させながら、実際のアプリケーションが要求するバリエーションのための十分な余地を残せる。これはまた、2.0 が 1.0 の透明性の原則を引き継ぐ方法でもある: フレームワークはブラックボックスではなく、開発者はそれを明確に理解し、その中に踏み込むことができる。

## 6. Workspace: 実行環境と Agent ロジックの分離

![Workspace: separate "what the agent does" from "where it runs"](/imgs/v2/as2-release-07.png)

agent の能力が高まるにつれ、それらはもはやモデルを呼び出すだけではなく — ツールを使い、ファイルにアクセスし、スキルをロードし、MCP サービスと話し、異なる環境で作業を実行する必要も出てくる。そのすべてが agent のランタイムロジックに焼き付けられていると、ローカル環境、コンテナ、あるいはクラウドサンドボックスの間の切り替えのたびに、繰り返し適応させることを強いられる。AgentScope 2.0 は、特に「agent が何をするか」と「どこで実行するか」を分離するために **Workspace** を導入し、実行環境を入れ替え可能で管理可能なシステムコンポーネントにする。

Workspace は、agent の実行環境のための AgentScope 2.0 の抽象化である。それはツール、MCP サービス、Skills ライブラリ、コンテキストの永続化を提供し、ローカルファイルシステム、Docker コンテナ、E2B クラウドサンドボックスといった異なる実行ストアを単一のインターフェースの背後に統一する。同じ agent は、ランタイムロジックを変更することなく、これらのどの環境でも実行できる。この設計は三つのポイントに集約される:

**第一に、統一されたインターフェース。** `WorkspaceBase` は、アイデンティティ、ライフサイクル、リソースの発見、コンテキストのオフロード、動的なリソース管理を抽象化する。各バックエンドは、AgentScope の実行システムにプラグインするために同じ一連のインターフェースを実装するだけでよい。

**第二に、結合よりも合成を優先する。** agent 自体は特定の Workspace に依存しない。それは Toolkit と受け取る指示を通じて、間接的にツールとリソースを使う。これにより、実行環境は入れ替え可能でありながら、agent のランタイムロジックは安定して移植可能なままである。

**第三に、プーリングのサポート。** Workspace にはウォームアップ用のプールが付属する: 実行環境はバッチで事前初期化でき、プールは acquire / release / invalidate-and-replace の操作を提供する。RL トレーニング中の並列ロールアウトのようなシナリオでは、これにより環境を繰り返し作成するコストを削減し、リソースの再利用とタスクのスループットを改善する。

Workspace により、agent はもはや単に「ツールを呼び出せる」だけではない。それらは **入れ替え可能で管理可能な実行環境** の中で作業し続けられる。ローカルマシン、コンテナ、クラウドサンドボックスの間を移動する必要がある複雑なタスクにとって、この抽象化は、安定した運用と柔軟なスケーリングのためのもう一つの基盤となる。

## 7. Agent Service: ローカルスクリプトからデプロイ可能なシステムへ

![Agent Service: standardized service interface + session log recovery + background tools](/imgs/v2/as2-release-08.png)

このリリースでは、AgentScope 2.0 は以前 AgentScope Runtime にあった Agent Service の機能をメインのライブラリに統合する。理由は直接的だ: 実世界のユースケースは、ターミナルや単一の Python プロセスでしか実行できない agent を必要としているのではなく — フロントエンド、外部アプリ、ワークフローシステムから確実に呼び出せる agent を必要としている。

以前、agent のコアロジックとランタイムサービスの機能が別々のスタックに分散していたとき、開発者はローカル開発、API のパッケージング、状態管理、ログの復元、サンドボックス実行、デプロイを絶えず縫い合わせなければならなかった。これらの機能を一つにまとめることで、AgentScope 2.0 はそのギャップを埋め、agent が **初日から** サービス対応、復元可能、観測可能、安全に実行できる形で構築されるようにする。

標準化されたサービスインターフェースにより、agent はその実行の進捗を外部にストリームでき、フロントエンドは実行をライブで表示できる。Session ログの復元により、タスクは中断後に続きから再開できる。バックグラウンドのツール実行により、長時間実行のツールがより確実に完了できる。Agent Service の統合は、agent がもはや単に「ローカルで実行できる」だけでなく — 異なるアプリケーションと実行コンテキストにプラグインする安定したサービスとしてデプロイでき、agent システムのためのランタイムサポート層になれることを意味する。

## おわりに: 透明な開発からシステムエンジニアリングへ

1.0 の *透明な開発* の原則を引き継ぎながら、AgentScope 2.0 はそのシステムレベルのアップグレードを一つの目標のもとに組織する: **agent がタスクを確実にやり遂げられるようにする** ことだ。モデル層でのリトライの仕組みから、実行環境の分離と抽象化まで。きめ細かい権限境界から、標準化されたサービス統合まで — それぞれのアップグレードは、実世界の agent が実際に必要としているもの、すなわち長時間実行、安全なツール利用、持続的なタスクの進行、外部アプリとのきれいな統合を、システム全体にわたって解決することを意図している。このリリースにより、AgentScope の焦点は「agent をどう構築するか」から「agent をどう確実に動かし続けるか」へと移っている。

この 2.0 リリースと並行して、AgentScope は多言語サポートも広げている。[Python](https://github.com/agentscope-ai/agentscope) 版はすでに 2.0 に更新されており([https://github.com/agentscope-ai/agentscope](https://github.com/agentscope-ai/agentscope))、[TypeScript 版の AgentScope](https://github.com/agentscope-ai/agentscope-typescript) も今では存在する([https://github.com/agentscope-ai/agentscope-typescript](https://github.com/agentscope-ai/agentscope-typescript))。AgentScope の Java 版もまもなく 2.0 に更新される予定だ。

AgentScope の上に構築された agent アプリケーションである QwenPaw も、近い将来 AgentScope 2.0 の基盤へとアップグレードされ、ユーザーにより安定した、より安全で、より拡張可能な agent 体験をもたらす。

AgentScope 2.0 は、スーパー agent アプリケーションのために、より堅固なシステム基盤を築きつつある。
